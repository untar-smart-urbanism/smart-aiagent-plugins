# Check go-live readiness

The final gate before production use, per playbook Section 6. Read `data/golive-gate.json` and `data/never-log.json` (relative to the installed `golive-gate` plugin).

## When to use

1. The user says "go live", "deploy", "launch", "release to the team", or "open access"
2. The user runs `/vibe-check`
3. Before helping configure production hosting, DNS, or user access for a tool

## Prerequisites (chain automatically — do not skip)

0. The repository conforms to the delivery pipeline's build contract → run `check-build-contract` at
   stage **`phase-7`** (the full set) and read `data/build-contract.json` for what it checks. Run it
   yourself as part of this gate; never hand the user a `/vibe-conform` instruction and wait. A **FAIL** (any
   High-severity item — a missing contract command, no `## Build and run` section in
   CLAUDE.md/AGENTS.md, a declared coverage report that resolves to no tracked file, a Dockerfile that
   never patches its base, the platform's injected CommonJS stubs, a dependency outside `allowedStack` with no tech-architect row in `## Stack Exceptions`) **stops this gate**: report the
   findings and NOT READY, because each one is fixable without entering the gate and every one of them
   shipped to production at least once on a repo that reached this point looking ready. A
   **CONDITIONAL** (Low/Medium only) does not stop the gate — carry the findings into the record.
   `gate-record-names-head` is the expected CONDITIONAL here: this run is what re-stamps it.
1. PROJECT.md `## Risk Level` is filled and **not Provisional**. If empty → run `assess-risk-level` first. If marked Provisional (intent-based, classified before code existed) → re-run `assess-risk-level` to verify against the now-existing codebase and finalize the tier.
2. The PROJECT.md dossier is substantially complete (owner, support contact, data used, login method, hosting). If key blocking sections are empty → run the `project-scaffold` plugin's `project-documenter` skill to complete the dossier from the codebase and owner input, then continue. A missing SRE-owned backup method is an advisory follow-up, not a prerequisite failure.
3. `docs/DESIGN.md` (the design-review document) exists and is current. If missing or stale → run the `project-scaffold` plugin's `design-document` skill to generate/refresh it from the codebase, the existing docs, and owner input, then continue. Run it **after** `project-documenter` — it reuses `docs/`. The document is produced for every tier; it only blocks the gate at Medium/High (see the `design-document-complete` item).
4. `docs/TEST-SCENARIO.md` (the test-case dossier) is generated and reconciled → run the `generate-test-scenarios` skill **after** `design-document` (scenarios align to a current DESIGN.md). It reconciles idempotently (PASSED-and-unchanged scenarios are kept — freshness now covers the generated test files too — PASSED-but-changed become STALE), generates and automatically runs hermetic test suites, runs the bounded High-severity fix loop (max 3 attempts per `data/test-policy.json`, then FAILED + NEEDS-HUMAN), and asks before running live/manual checks or looping Medium/Low failures. Because the fix loop can modify product code, this prerequisite runs **before** the review-proof prerequisite — fixes applied here make an already-sealed proof stale, so at Medium/High get this phase green and committed before the independent reviewer runs `/vibe-review` (the reviewer also verifies the human-judgment scenarios). Produced for every tier; it only blocks the gate at Medium/High (see the `test-scenario-complete` item).
5. A reviewer-sealed proof exists for the current commit (`docs/REVIEW-PROOF.md`), per tier:
   - **Low** → **run `seal-review-proof` now** (self-certify) so the proof is produced as part of this gate. Do not require a separate manual step.
   - **Medium/High** → the proof must **already exist**, sealed by an independent reviewer. If missing → **stop with NOT READY**: "an independent reviewer must run `/vibe-review`." Never self-run it for Medium/High: the reviewer seals under their own git identity in their own checkout, and this gate cannot establish that identity on their behalf.

**Complete the entire prerequisite chain above before verifying and recording below.** The steps that follow verify the tool's **current** state and write the result into PROJECT.md, so every artifact the chain creates or refreshes (the dossier, `docs/DESIGN.md`, `docs/TEST-SCENARIO.md`, `docs/REVIEW-PROOF.md`) must be on disk first. Never verify or record while a prerequisite is still pending, and never carry a "missing" observation made at entry into the record — re-read the files after the chain has run.

## Steps

1. **Load** `data/golive-gate.json`; select items whose `appliesTo` includes the tier.
2. **Verify approvals per tier** (`approvals-complete`, using its `tierDetail`):
   - Low: owner self-check recorded.
   - Medium: independent review recorded — the recorded reviewer is neither the Project Owner nor the Support Contact (per `review-proof.json` `independence`).
   - High: the formal Tech R&D/Architecture, SRE, Information Security, and GRC (as applicable) review recorded in Review Evidence, and the formal approval task approved by one of `risk-criteria.json` `tiers[high].formalApproval.approvers` (one is enough).
   - **Tier used**: the BPT-confirmed level when `## Risk Level` records one (`bpt-risk-confirmed`), else the assessed level. A BPT login outside `bptConfirmation.confirmers` does not count.
   - `bpt-risk-confirmed`, `triage-review`, `dpia-recorded` (High with specific personal data), `ai-usage-recorded` (Medium/High) and the advisory `review-lead-time` (14 days) follow their `rule` in `data/golive-gate.json`. A missing human confirmation or approval is CONDITIONAL, not FAIL.
3. **Verify each gate item** against its `projectMdSection` in PROJECT.md, marking **PASS / FAIL / NEEDS-HUMAN** with one line of evidence; an advisory item may be **NEEDS FOLLOW-UP**. **Re-read each item's `projectMdSection` and `docFile` from disk at this point** — the prerequisite chain may have just created or refreshed them (`docs/DESIGN.md`, `docs/TEST-SCENARIO.md`, `docs/REVIEW-PROOF.md`, the dossier), so verify against the current on-disk state, never an assessment made before the chain ran. **For any human-only blocking item whose section is empty or unverifiable and whose value the owner can supply directly — Access Status, Login Method, **Project Owner**, Support Contact, and the labels — ask the owner for it now and record it, then re-verify** (the same active-ask the `gcp-label-set` item uses); do not mark it FAIL without asking first. Items that need an external artifact — recorded approvals / sign-offs (`approvals-complete`) and Review Evidence — cannot be filled by asking and remain CONDITIONAL/FAIL until the real record exists.
   - `sso-login-only`: Login Method must be one of the `allowed` values — no other method is permitted.
   - `useful-logs-no-secrets`: scan code and log configuration for `never-log.json` items being logged.
   - `backup-recovery`: SRE owns the backup pipeline or method. Missing status or reference is **NEEDS FOLLOW-UP**, never a blocker by itself. Record SRE as owner and any tracking ticket; keep application rollback steps separately where known.
   - `design-document-complete` (Medium/High): verify the item's `docFile` `docs/DESIGN.md` exists and the views required for the tier (per its `tierDetail`) are present — component + access-boundary deployment diagram, sequence diagrams for the main use cases, and for High the transaction-flow diagram plus a completed (or owner-confirmed N/A) Financial Risks section. Missing file or a missing required view → **FAIL** — but the file is produced by the chained `design-document` prerequisite, so check what is on disk **after** the chain, never a pre-chain note. Do **not** verify reviewer sign-offs here — they are covered by `approvals-complete`.
   - `test-scenario-complete` (Medium/High): verify the item's `docFile` `docs/TEST-SCENARIO.md` exists, covers the DESIGN.md use-case flows, and has **no important/sensitive scenario in FAILED or STALE state**. A STALE scenario means code changed since it last passed — treat it as not-yet-verified → **FAIL** until re-run via `generate-test-scenarios`. A `FAILED (…, NEEDS-HUMAN)` scenario blocks exactly like any FAILED; the annotation routes it to a human, it never waives it. Severity maps from category per `data/test-policy.json`. For **High**, every `sensitive` scenario must be **PASSED** (not PENDING). Missing file → **FAIL**: "run `/test-scenarios`" — but the file is produced by the chained `generate-test-scenarios` prerequisite, so confirm what is on disk **after** the chain, never a pre-chain assessment. For **Low**, N/A (the dossier is still generated by the chained skill but does not block).
   - `review-proof-sealed` (Medium/High): verify the item's `docFile` `docs/REVIEW-PROOF.md` exists, its verdict is **PASS**, its recorded independence result is **HOLDS** or **HOLDS-PARTIAL**, and it is **fresh** — `git diff --name-only <reviewed-commit>..HEAD` (using the proof's recorded `reviewed-commit`) lists only `docs/REVIEW-PROOF.md`, `PROJECT.md`, and `vibe-release.json` (the release doc is regenerated and committed as part of the same review handoff); any other tracked-source change → **stale → FAIL**. **Re-run the independence comparison** against the *current* `## Project Owner` / `## Support Contact` using `review-proof.json` `identityMatching`: the staleness rule deliberately permits `PROJECT.md` to change between sealing and this gate, and those sections are the *input* to the independence rule, so an owner/support edit made after sealing is invisible to staleness and must be re-checked here. Reviewer now matches the owner or the support contact → **FAIL**: "the sealed reviewer is now the Project Owner or Support Contact — an independent reviewer must re-run `/vibe-review`." A reviewer who **is** a repo commit author but is neither owner nor support contact **passes** — prior authorship never fails this item. Missing, non-PASS, independence VIOLATED/UNDETERMINED, or stale → **FAIL**: "an independent reviewer must run `/vibe-review`." For **Low**, this item is N/A (the proof was just produced by the chained `seal-review-proof`).
   - `ownership-support-contacts`: both sections must be filled **and** match the formats in the item's `fields` map — this is the gate that enforces them, because the owner runs `/vibe-check` and can fix them here.
     - **`## Project Owner` must be a single GitHub username** (per `fields.project-owner`): validate the pattern, confirm the login exists and is a `User` not an `Organization` (`gh api users/<login> --jq .type`), and confirm acme-org-ops org membership (`gh api -i orgs/<org>/members/<login>`; read the org from `ops-github`'s `github-policy.json` `defaultOrg` when installed). An inconclusive membership result is **UNVERIFIED → warn, do not FAIL** (see `onUnverified`); a confirmed non-member, a non-existent login, or a format violation → **FAIL**.
     - **`## Support Contact` must be a single email address** (per `fields.support-contact`): a `deniedDomains` match (public webmail) or a `deniedLocalPatterns` match (shared lab/sandbox/numbered group accounts such as `alpha.lab01@…` — nobody is accountable behind them) → **FAIL**. A `warnLocalPatterns` match (a role or queue mailbox like `ops-helpdesk@`) **passes** with a one-line note that a named individual is preferred.
     - **Empty, placeholder, or format-violating → ask the owner now and rewrite the section, then re-verify** (per `askIfMissing`). For Project Owner, resolve the running user's login with `gh api user --jq .login` and ask "Is the project owner you (`<login>`)?" — record it on yes, ask for the owner's username on no. For a legacy free-text value, show what is currently recorded and ask which GitHub username it corresponds to; **never guess a login from a person's name.** Still unanswered → FAIL.
   - `gcp-label-set`: PROJECT.md `## Label` must record all three sub-fields in the item's `labels` map (GCP cost/budget attribution). **Company** must be exactly one of `labels.gcp-label-company.allowed` (sister-company code); **Division** must be exactly one of `labels.gcp-label-div.allowed` (operations | finance | marketing | commercial); **Department** is free text and must be non-empty. Any field empty or invalid → **ask the owner for that value now** and record it, then re-verify; never pick a value for the owner. Still unanswered → the item FAILs.
   - Other items: the mapped section is filled and consistent with the checklist wording.
4. **Check the remediation backlog** (`remediation-blocking-clear`, for brownfield-adopted projects):
   - Locate the backlog per `data/remediation-tiers.json` `backlogFile` rules: the pointer line in PROJECT.md Security Notes first, then the default path whose first line is the marker. No backlog → the item passes as **N/A** (project was never brownfield-adopted).
   - Any finding with status OPEN under `## Blocking` → the item **FAILs** and the verdict cannot be READY; list each open BLOCKING finding (ID, title, location) among the blocking items.
   - A WAIVED blocking finding counts as clear **only if** the waiver names an Information Security approver and a matching entry exists in `## Review Evidence`; otherwise treat it as OPEN and say why.
   - Open ADVISORY findings never block; include their count and IDs in the gate record ("Advisory backlog at gate time: ... — documented, migration in progress").
5. **Verdict**:
   - **READY** — all applicable blocking items pass and approvals are recorded; an advisory SRE backup follow-up may remain open.
   - **NOT READY** — list blocking items and what fixes each.
   - **CONDITIONAL** — agent-checkable items pass but human approvals are pending; name the missing approvers.
6. **Record**: append a dated gate record (verdict, item results, SRE backup follow-up if open, advisory backlog IDs, checked-by) to PROJECT.md `## Review Evidence`, **reflecting the post-chain state**. If an artifact was missing when the gate started but a chained prerequisite created it during this run (`docs/DESIGN.md`, `docs/TEST-SCENARIO.md`, `docs/REVIEW-PROOF.md`), record it as present/PASS and supersede the entry-time observation — never record as missing something the same run just created. Append only — never delete earlier entries, never create a new governance file.
7. **Generate the release document** — write `vibe-release.json` at the project root per `data/release-doc.json`, on **every** gate run regardless of verdict. It is our governance record plus registry data — never tell the user this file gates their deployment:
   - Check the working tree: if dirty, warn that uncommitted changes were NOT evaluated by this gate — recommend committing and re-running. The hash always refers to HEAD.
   - The document is a **flat, single-level** object — every field is a top-level key, no nested objects.
   - `git rev-parse HEAD` → `target-commit-hash`; today's date → `generated-at`.
   - `review-gate` = `reviewGateByRisk[tier]`; `release-gate-status` = the verdict (READY | CONDITIONAL | NOT-READY); `project-status` = `projectStatusByVerdict[verdict]`.
   - `review-verdict` / `review-proof` / `reviewed-at` — read from `docs/REVIEW-PROOF.md` and the latest PROJECT.md `## Review Evidence` entry: the sealed verdict (PASS | FAIL | INCOMPLETE), `docs/REVIEW-PROOF.md`, and the sealed date. No proof → each is `null` (never invented, same policy as the project fields). These are our governance record; the platform does not read them.
   - `start-vibe` — PROJECT.md `## Vibe Start` when present; else fall back to the earliest git commit's author date: `git log --reverse --date=short --format=%ad | head -1`. Never invented beyond these two derivations.
   - Fill the flat project fields (`project-name`, `project-owner`, `support-contact`, `gcp-label-company`, `gcp-label-div`, `gcp-label-dept`, `project-scope`, `risk-level`, `project-status`, `app-web-url`, `repo-url`, `live-version`) from PROJECT.md sections (the three labels come from the `## Label` Company/Division/Department lines), `git remote get-url origin`, and the package.json version per the spec's field map. A missing dossier value → `null`, never invented.
   - Full overwrite each run — it is a derived artifact, not a log; history lives in git.
   - **Do not auto-commit.** Tell the user: "vibe-release.json written for commit `<hash>` — commit and push it (e.g. /push-github). This record evaluated `target-commit-hash`; if you commit more code, re-run the gate so the verdict still describes what you are shipping."

## Hard rules

- You verify that human approvals are **recorded** — you never grant them.
- Never certify readiness when a FAIL or missing approval exists, even if the user insists; record the exception instead.
- An open BLOCKING backlog finding is a FAIL even if every other gate item passes. Never reclassify a finding's tier at gate time — tiers come from `data/remediation-tiers.json`.
- `vibe-release.json` reflects this gate run only — never hand-edit `release-gate-status` or `target-commit-hash`; re-run the gate instead.
- Never claim this gate blocks a platform deployment. `release-gate-status` is our verdict, enforced by people and process; the deployment platform's production gate is separate. Overstating our reach teaches users to trust a control that is not there.
- The recorded result reflects the **current** state after the prerequisite chain completes. Never record — or certify — an artifact as missing when a chained prerequisite created it during this same run; re-read from disk and record what is actually there, so PROJECT.md always reflects the latest update.
