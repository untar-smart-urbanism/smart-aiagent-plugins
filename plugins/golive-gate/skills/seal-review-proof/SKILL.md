# Seal review proof

Runs the playbook's Section 5 checklist as a **reviewer-driven** flow and seals the result to `docs/REVIEW-PROOF.md`, bound to the current commit and to the reviewer's git identity. Read `data/review-proof.json`, `data/review-checklist.json`, and `data/never-log.json` (relative to the installed `golive-gate` plugin).

This complements `review-before-release` (which the builder runs to gather evidence): here the **reviewer** runs the flow and produces the sealed proof.

## When to use

1. The user runs `/vibe-review`.
2. An independent reviewer is about to sign off a tool before it is shared, merged, or released.
3. `check-golive-readiness` needs a sealed proof: for Low it chains this skill automatically; for Medium/High it requires the proof to already exist.

## Steps

1. **Preconditions.**
   - Read the tier from PROJECT.md `## Risk Level`. Empty → run `assess-risk-level` first. Marked **Provisional (intent-based)** → re-run `assess-risk-level` to finalize against the now-existing code before sealing.
   - The working tree must be **clean**. If dirty, refuse: "commit your work first — the proof binds to a commit." Do not seal a dirty tree.
2. **Reviewer identity.** Read `git config user.name` and `git config user.email`, and resolve the reviewer's GitHub login with `gh api user --jq .login`. State it plainly: "signing as `<name> <email>` (GitHub `<login>`)." If the git name or email is unset, stop and ask the reviewer to configure their git identity. If `gh` is unauthenticated the login cannot be resolved — say so, because the project owner is recorded as a GitHub username and that comparison then cannot be made (see step 3).
3. **Independence** (per `review-proof.json` `independence`) — the reviewer may be **anyone except the project owner or the support contact**. Being a repo commit author is **not** disqualifying; prior authorship of this tool never blocks a seal.
   - **Resolve the exclusion set** (`ownerSupportResolution`): for each of project owner and support contact, take `vibe-release.json`'s `project-owner` / `support-contact` when that file exists and the field is non-null; otherwise PROJECT.md `## Project Owner` / `## Support Contact`. The fallback is the normal path on a first review — the chained gate in step 10 is what writes `vibe-release.json`, so it legitimately does not exist yet. A section holding nothing, only the template HTML comment, or a placeholder (`TBD`, `N/A`, `-`) counts as **empty**. **Never ask the reviewer to supply these values** — the exclusion set must not be reviewer-nominated.
   - **Compare** the step-2 reviewer identity against every exclusion-set entry using `independence.identityMatching`. **STRICT** is the normal path, because the gate enforces the formats: `## Project Owner` is a **GitHub username** → compare case-insensitively against the reviewer's GitHub login; `## Support Contact` is an **email** → compare by exact lowercase equality against the reviewer's git `user.email` (and their `gh api user --jq .email` when non-null). No fuzzy matching, no near-miss question — an exact identifier either matches or it does not. If `gh` is unauthenticated the owner comparison is **UNDETERMINED**: do not fall back to name matching and do not pass, since the reviewer could be the owner.
   - **LEGACY fallback** — only when a field is free text that fails its format (an old dossier). Use the token-compatible name rule ("A. Owner" matches "App Owner", "A. R." matches nobody), never infer a person from a shared mailbox's local part, and ask the near-miss question when the rule prescribes it. Record the format violation as an observation and tell the reviewer that `/vibe-check` will ask the owner to reformat it — **you must not edit those fields yourself.**
   - **Medium/High:** `VIOLATED` (the reviewer is the project owner or the support contact) → **refuse to seal, write no proof**, and report that someone who is neither must run `/vibe-review`. `UNDETERMINED` → do **not** approve: carry it to a verdict of **INCOMPLETE**. Two causes, each with its own fix: neither field resolvable → "fill PROJECT.md `## Project Owner` / `## Support Contact`, then re-run `/vibe-review`"; the owner is a GitHub username but `gh` is unauthenticated so your login is unknown → "run `gh auth login`, then re-run `/vibe-review`". Never treat an unobtainable reviewer identity as a non-match. `HOLDS` / `HOLDS-PARTIAL` → proceed.
   - **Low:** self-review is allowed; record "self-review" in the proof and skip the comparison.
   - **Team/alias-only owner or support contact** (`teamOrMailboxOnlyCase`): independence HOLDS against the stated identities, but say so in the proof with the remedy — name an individual in PROJECT.md to make the check person-level.
4. **Anchor.** `git rev-parse HEAD` → `reviewed-commit`. No range, no digest.
5. **Run the checklist.** Load `data/review-checklist.json`; select items whose `appliesTo` includes the tier. Reuse the verification recipes from `review-before-release` (its step 4):
   - **Agent-checkable** items (`verify: agent` / `human+agent`) — verify live against the repo, one line of evidence each: grep source, sample data, docs, and log statements for `never-log.json` `scanHints` and for secrets (flag real values, not variable names); `git remote -v` points to `github.com/acme-org-ops`; a rollback point exists (git tag, release, or saved branch); `## Project Owner` and `## Support Contact` are filled and in the required formats — a GitHub username and an email respectively (`golive-gate.json` item `ownership-support-contacts`, `fields`); a format violation is reported here but fixed by the owner at `/vibe-check`, not by you; the intended data sources are used.
   - **Human-judgment** items (`verify: human`) — ask the reviewer one at a time (requirements met, main function tested, correct data, access restricted, and for High all approvals complete). Record PASS / FAIL / NA / NEEDS-HUMAN with a one-line note. For **main-function-tested**, use `docs/TEST-SCENARIO.md` as the evidence source (its `evidenceSource`): confirm the agent-checkable scenarios are PASSED, verify the `verify: human` scenarios yourself, and mark each in the dossier (`PASSED (<date>, <commit>, <reviewer name>)` / `FAILED`). This item passes only when no important/sensitive scenario is FAILED or STALE (High/Medium severity; a NEEDS-HUMAN annotation still counts as FAILED).
6. **Verdict** (per `review-proof.json` `verdictValues`): **PASS** iff every applicable item passes and independence is `HOLDS` or `HOLDS-PARTIAL`; **FAIL** if any applicable item fails; **INCOMPLETE** if items are unanswered or independence is `UNDETERMINED`. On FAIL/INCOMPLETE still write the proof, marked not-approved, with the blocking items listed.
7. **Write `docs/REVIEW-PROOF.md`** per the `template` in `review-proof.json` (overwrite; latest-only). In `## Reviewer`, record the exclusion set actually compared against — quoted, with its source — and the independence result, so a reader can audit the basis of the check. Include the attestation-grade limitation note from `independence.limitation`.
8. **Append to PROJECT.md `## Review Evidence`** a single dated summary line per `review-proof.json` `reviewEvidenceSummary` (date, reviewer, tier, verdict, short `reviewed-commit`, link to `docs/REVIEW-PROOF.md`, independence result). Append-only per `rules/project-dossier.mdc` — never rewrite earlier entries.
9. **Seal** (per `review-proof.json` `sealPolicy`): show the reviewer exactly what will be committed, then stage `docs/REVIEW-PROOF.md` + `PROJECT.md` and create the sealing commit **as the reviewer's git identity**. Do **not** push yet — a second commit follows in step 11. The commit author is the verifiable seal.
10. **Regenerate the release document** (only when a proof was sealed in step 9 — skip on a self-certification refusal). Chain `check-golive-readiness` against the just-sealed commit (HEAD): it re-reads this proof to fill `review-verdict` / `review-proof` / `reviewed-at`, evaluates every gate item for `release-gate-status`, sets `target-commit-hash` to the sealed commit, and overwrites `vibe-release.json`. The gate's prerequisites (risk level, dossier, `docs/DESIGN.md`, `docs/TEST-SCENARIO.md`) are already satisfied from the builder's earlier `/vibe-check`, so it evaluates rather than regenerates them. This automates the otherwise-manual `/vibe-check` re-run so the review outcome reaches `vibe-release.json` immediately.
11. **Commit the release document** (same condition as step 10). The chained gate writes `vibe-release.json` but does not commit it; `/vibe-review` must not leave the handoff with an uncommitted or stale release doc. Show the reviewer the staged file, then create a **second commit** — `vibe-release.json` only — under the reviewer's git identity. This mirrors the `/vibe-check` path exactly: `target-commit-hash` points at the seal commit (step 9), and `vibe-release.json` sits one commit above it. By the end of `/vibe-review` both commits exist. Do **not** push — tell the reviewer to push both (e.g. `/push-github`) so the sealed review is recorded in the repo alongside the app's platform labels.

## Output

- **PASS** — `docs/REVIEW-PROOF.md` written and sealed (commit 1); `vibe-release.json` regenerated with `review-verdict: PASS` and a consistent `release-gate-status` / `target-commit-hash`, and committed (commit 2); the tool is reviewer-approved for `reviewed-commit`. Tell the reviewer to push both commits, and that changing tracked source after them invalidates the proof (the gate re-checks staleness).
- **FAIL / INCOMPLETE** — the proof lists each blocking item and what fixes it; `vibe-release.json` is regenerated with the not-approved verdict (`release-gate-status: NOT-READY`) and committed; the tool is not approved.
- **Refused (self-certification)** — no proof written, no commits, and `vibe-release.json` is **not** touched; Medium/High needs a reviewer who is neither the project owner nor the support contact. Being a repo commit author is **not** by itself a refusal reason.

## Hard rules

- Never seal a Medium/High proof when the reviewer is the stated project owner or support contact — that is self-certification. Prior authorship of this repo is **not** disqualifying and never blocks a seal.
- Never treat an empty owner/support contact as independence satisfied — an unresolvable exclusion set is `UNDETERMINED` → INCOMPLETE, never PASS.
- Never let the reviewer supply the project owner or support contact; resolve them only from `vibe-release.json` and PROJECT.md.
- Never seal a dirty working tree — the proof must bind to a committed state.
- For High risk, formal Architecture/Tech R&D, SRE, and Information Security sign-offs are still required and are verified as recorded by `check-golive-readiness` — this skill does not grant them.
- This skill never *computes* `release-gate-status` or `target-commit-hash` itself — it regenerates `vibe-release.json` only by chaining `check-golive-readiness` (step 10), which owns those fields. Never hand-edit the release doc.
