# Code Review (OWASP)

Applies the [OWASP Secure Coding Practices Checklist](https://owasp.org/www-project-secure-coding-practices-quick-reference-guide/stable-en/02-checklist/05-checklist) on every code change and user prompt.

## Purpose

- **Auto-apply** OWASP secure coding on every coding task — users do not need to request security review
- **Audit** existing projects manually when needed

## Agent behavior (automatic)

When an agent plans or writes code:

1. Read skill `apply-secure-coding` and `data/owasp-checklist.json`
2. Apply security requirements **while coding**, not only at the end
3. Verify applicable checklist sections before finishing the task
4. Fix violations immediately

The `owasp-secure-coding` rule (`alwaysApply: true`) enforces this on every session when installed.

## Manual commands (existing projects)

| Command | Scope | Purpose |
|---------|-------|---------|
| `/review-code` | Changed/selected files | PR or diff review |
| `/audit-security` | Entire codebase | Legacy repo or pre-release audit |

## Components

| Component | Purpose |
|-----------|---------|
| `data/owasp-checklist.json` | 26 sections, 327 checklist items (OWASP core + org API/PAN/AI + security patterns) |
| `data/trusted-automation.json` | Registered automation committers (CI/CD bots) — authorized activity/paths for committer-provenance audits |
| Skill `apply-secure-coding` | **Continuous line-level enforcement during coding** |
| Skill `apply-security-patterns` | **Design-level patterns** for sensitive-data / auth / secret features |
| Skill `owasp-code-review` | Structured manual audits |
| Rule `owasp-secure-coding` | Always-on enforcement |
| Rules `owasp-backend/frontend-security` | App-scoped security rules |
| Agent `secure-code-reviewer` | Security enforcement subagent |
| Command `review-code` | Manual diff-scope review |
| Command `audit-security` | Manual full-repo audit |

## `apply-security-patterns`

Where `apply-secure-coding` covers *how to write a safe line* (validate, encode, parameterize),
`apply-security-patterns` covers *how to shape a safe feature* when it touches sensitive data,
identity, authentication, secrets, or bulk access. Nine stack-agnostic patterns — envelope
encryption at rest, blind index, PII exposure minimization, session/token revocation, CSRF
defense-in-depth, secrets management, audit logging, per-actor rate limiting, container/Pod
hardening — each with its **residual risk** documented (see
`skills/apply-security-patterns/references/security-patterns.md`).
Their verifiable checklist items live as the security-pattern sections of `data/owasp-checklist.json`.

Pattern 9 is split by ownership, because the two halves live in different repositories: the
**`Dockerfile`** is ours and exists before onboarding, so we author and enforce it; the **Pod and
Deployment manifests** are generated by the deployment platform in `deployment-<app>` at onboarding, so we
review and remediate what Trivy reports there and never author them. A pre-onboard project having no
manifests is the expected state, not a finding.

## Trusted automation registry

`/audit-security` classifies every committer in git history as **human**, **registered automation**,
or **unregistered automation** using `data/trusted-automation.json`. Registered identities (e.g. the
platform deployment bot `DevOps Platform AI <devops-ai@platform.local>`) acting within their
`authorizedActivity` and `authorizedPaths` are expected automation — reported informationally, not as
findings. Unregistered non-human committers, or registered identities committing outside their scope,
are **must-fix**.

Identity recognition ≠ content exemption: git identity is spoofable (attestation-grade), so the
registry never skips checklist evaluation of any commit's content.

Register a new identity by PR to this repo (plugins-team review): add an `identities[]` entry with
`name`, `emails`, `type`, `operator`, `authorizedActivity`, `authorizedPaths`, `neverAuthorized`,
`approvedBy`, `approvedOn`. Scope changes are made by editing the registry, never ad hoc during an audit.

## Data

Edit the checklist directly in `data/owasp-checklist.json` — it is hand-maintained (the OWASP core,
plus the org's API/PAN/AI and security-pattern sections). The build script only regenerates the
OWASP-only base from markdown and **overwrites** the file, dropping the hand-maintained sections, so
use it for reference only:

```bash
node plugins/code-review/scripts/build-checklist-json.js
```

`data/trusted-automation.json` is hand-maintained policy as well — change it only via reviewed PR.

## Install

```text
/add-plugin code-review
/plugin install code-review@smart-aiagent-plugins
```

Works with `tech-radar`, `code-structure`, and `scan-dependency` plugins.
